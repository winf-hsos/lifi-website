Das Modul lifi_hardware

Die Hardware, die ihr benutzt, stammt von der Firma Tinkerforge, und die liefert eine eigene Programmierschnittstelle mit. Damit könntet ihr direkt arbeiten. Ihr werdet es aber nicht tun, jedenfalls nicht am Anfang.

Warum es das Modul gibt

So sieht ein Programm aus, das mit der Tinkerforge-Schnittstelle eine Farbe setzt und einen Messwert holt:

from tinkerforge.ip_connection import IPConnection
from tinkerforge.bricklet_rgb_led_v2 import BrickletRGBLEDV2
from tinkerforge.bricklet_color_v2 import BrickletColorV2

HOST = "localhost"
PORT = 4223
UID_LED = "ABC"       # steht auf dem Bauteil bzw. im Brick Viewer
UID_SENSOR = "XYZ"

ipcon = IPConnection()
led = BrickletRGBLEDV2(UID_LED, ipcon)
sensor = BrickletColorV2(UID_SENSOR, ipcon)
ipcon.connect(HOST, PORT)

led.set_rgb_value(255, 0, 0)
r, g, b, c = sensor.get_color()
print(r, g, b, c)

ipcon.disconnect()

Dasselbe mit dem Modul:

from lifi_hardware import led, sensor

led.set_color(255, 0, 0)
print(sensor.read())

Der Unterschied sind nicht nur ein paar Zeilen. In der oberen Fassung stehen mindestens fünf Dinge, die ihr in Woche zwei unmöglich verstehen könnt: was eine IP-Verbindung ist, warum ein Programm auf dem eigenen Rechner eine Netzwerkadresse braucht, was ein Port ist, was eine UID ist und woher man sie bekommt, und warum man am Ende wieder trennen muss.

Nichts davon ist Thema dieses Moduls. Es wäre Ballast, den ihr mitschleppt, ohne dass er euch etwas beibringt. Das Modul nimmt euch diesen Teil ab und lässt genau das übrig, worum es tatsächlich geht: Licht erzeugen, Licht messen, und die zwei Einstellungen, mit denen ihr die Messung beeinflusst.

Was das Modul euch nicht abnimmt

Es versteckt nicht alles, und das ist Absicht. Die beiden Einstellungen des Sensors bleiben sichtbar, weil an ihnen der wichtigste Zielkonflikt des Projekts hängt. Wer sie nie zu Gesicht bekommt, kann seinen Durchsatz nicht optimieren.

Installieren und aktualisieren

Das Modul liegt in einem GitHub-Repository und wird von dort installiert:

pip install git+https://github.com/winf-hsos/lifi-hardware.git

Die Tinkerforge-Bibliothek kommt dabei als Abhängigkeit automatisch mit.

Im Lauf des Semesters kann es neue Fassungen geben, etwa wenn eine Funktion dazukommt oder ein Fehler behoben wird. Den neuen Stand holt ihr euch so:

pip install --upgrade --force-reinstall git+https://github.com/winf-hsos/lifi-hardware.git

Die Schnittstelle

Für den Einstieg genügt eine Zeile, die zwei Objekte hereinholt:

from lifi_hardware import led, sensor

Beide verbinden sich beim ersten Gebrauch selbst mit eurem Gerät; ihr braucht keine Adressen, keine Kennungen, keine Konfiguration. Am Programmende geht die LED automatisch aus, und die Verbindung wird sauber getrennt.

Die LED (der Sender)

led.set_color(r, g, b)   # jeder Wert 0 bis 255
led.off()                # dasselbe wie led.set_color(0, 0, 0)
led.color                # aktuelle Farbe als (r, g, b), von der Hardware gelesen

Eine gesetzte Farbe bleibt an, bis etwas anderes kommt, auch über das Programmende eures Skripts hinaus, wenn ihr nicht aufräumt. led.color fragt die Hardware selbst, nicht einen gemerkten Wert; das hilft bei der Fehlersuche, wenn ihr wissen wollt, was gerade wirklich leuchtet.

Der Sensor (der Empfänger)

reading = sensor.read()          # Reading(r, g, b, c), jeder Wert 0 bis 65535
r, g, b, c = sensor.read()       # lässt sich direkt in vier Variablen auspacken

sensor.set_integration_time(ms)  # erlaubt: 2.4, 24, 101, 154 oder 700
sensor.set_gain(factor)          # erlaubt: 1, 4, 16 oder 60
sensor.integration_time          # aktuelle Einstellung nachsehen
sensor.gain                      # aktuelle Einstellung nachsehen
sensor.set_light(True)           # weiße Beleuchtungs-LED des Sensors

Vier Dinge muss man über den Sensor wissen. Erstens misst er vier Kanäle, nicht drei: Rot, Grün und Blau sind gefiltert, der vierte Kanal c (Clear) misst ungefiltert und ist deshalb der empfindlichste. Zweitens entsprechen die Messwerte nicht den gesendeten RGB-Werten; dazwischen liegen überlappende Filter, der Abstand und das Umgebungslicht, und genau deshalb kalibriert ihr. Drittens misst der Sensor in seinem eigenen Takt, eine Messung je Integrationszeit: read() holt die jüngste fertige Messung ab und wartet nicht. Wer öfter liest, als der Sensor misst, bekommt denselben Wert mehrfach; neue Information gibt es höchstens einmal je Integrationszeit. Viertens startet der Sensor immer in einem bekannten Zustand (Verstärkung 16, Integrationszeit 154 ms, Beleuchtungs-LED aus), damit Messreihen vergleichbar sind. Welche Einstellungen zu eurer Strecke passen, sagt euch nur eure eigene Messreihe.

Die kleine weiße Beleuchtungs-LED am Sensor ist übrigens dafür gedacht, Gegenstände anzuleuchten, deren Oberflächenfarbe man messen will. Für eure Lichtstrecke stört sie nur, deshalb ist sie beim Start aus, und ihr lasst sie aus.

Mehr Kontrolle, wenn ihr sie braucht

Wer selbst bestimmen will, wann verbunden und getrennt wird, nimmt statt der zwei bequemen Objekte die Klasse dahinter:

from lifi_hardware import LifiDevice

lifi = LifiDevice.connect()      # findet LED und Sensor selbst
lifi.led.set_color(255, 0, 0)
print(lifi.sensor.read())
lifi.close()                     # LED aus, Verbindung getrennt

connect() kennt außerdem ein paar Optionen, etwa log_file=None (kein Messprotokoll) und server=None (kein Upload, dazu gleich mehr).

Das Messprotokoll und das Cockpit

Alles, was euer Gerät tut, schreibt das Modul in eine Datei namens lifi_log.jsonl in dem Ordner, in dem euer Programm läuft: jede gesetzte Farbe, jede Messung, jede Einstellungsänderung, als eine Klartext-Zeile pro Ereignis. Das ist euer Messreihen-Gedächtnis, es gehört euch, und es funktioniert immer, auch ganz ohne Internet.

Zusätzlich schickt das Modul dieselben Ereignisse an den Kursserver. Damit seht ihr eure eigene Strecke live im Browser, im Team-Cockpit: oben, was eure LED sendet, darunter, was euer Sensor misst, auf einer gemeinsamen Zeitachse. Wenn die beiden nicht zusammenpassen, schaut ihr gerade auf euren Fehler; das Cockpit ist euer wichtigstes Werkzeug für die Fehlersuche an der Strecke. Ruft es mit eurem Teamnamen auf: https://lifi.uber.space/cockpit?team=euer-team.

Dabei gilt volle Transparenz: Hochgeladen wird exakt das, was auch in eurer lokalen Datei steht, keine Zeile mehr. Stürzt euer Programm ab, geht zusätzlich der Fehlertyp mit einer bereinigten Meldung mit (Dateipfade werden vorher entfernt, euer Quelltext geht niemals mit); der Fehler erscheint dann als rote Marke in eurem Cockpit. Wer den Upload nicht möchte, schaltet ihn jederzeit und ohne Nachteil ab, mit LifiDevice.connect(server=None) oder der Umgebungsvariable LIFI_SERVER=off; das lokale Protokoll läuft davon unberührt weiter.

Schaut hinein

Das Modul ist kein Zaubertrick. Es ist überschaubarer Python-Code, den ihr öffnen und lesen könnt, und spätestens ab Challenge 2 solltet ihr das auch einmal tun. Der Quelltext liegt offen im selben GitHub-Repository, aus dem ihr das Paket installiert habt. Ihr werdet darin genau die Zeilen wiederfinden, die oben im ersten Beispiel stehen.

Das ist ein Muster, das euch im Studium ständig begegnen wird: Unter jeder bequemen Schnittstelle liegt eine unbequemere, und darunter wieder eine. Die Tinkerforge-Schnittstelle versteckt ihrerseits, wie die Daten tatsächlich über das USB-Kabel laufen. Und darunter geht es weiter bis zu einzelnen Spannungspegeln auf einer Leitung.

Wenn ihr später einmal etwas braucht, was das Modul nicht kann, dürft ihr jederzeit eine Ebene tiefer greifen und die Tinkerforge-Schnittstelle direkt benutzen. Verboten ist das nicht. Ihr müsst es nur nicht am ersten Tag tun.
